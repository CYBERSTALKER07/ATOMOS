## 2. ParentOrders Saga & Multi-Supplier Cart Rollup

### 2.1. The Distributed Rollup Problem

#### What it is
In wholesale retail, a store owner frequently needs to order dairy from Supplier A, beverages from Supplier B, and confectionery from Supplier C within a single checkout session.

#### How it works
The `ParentOrders` aggregate (`file:///Users/shakhzod/Desktop/V.O.I.D/pegasusX/apps/backend-go/schema/spanner.ddl:222-235`, `apps/backend-go/order/service.go:168-171`) coordinates this multi-supplier transaction as an orchestrated saga:

```
+----------------------------------------------------------------------------------------------------+
|                                      PARENT ORDERS SAGA LIFECYCLE                                  |
+----------------------------------------------------------------------------------------------------+
|                                                                                                    |
|  [Retailer Checkout Action] (POST /v1/retailer/cart/checkout)                                      |
|         |                                                                                          |
|         v                                                                                          |
|  [Create ParentOrder in Spanner]                                                                   |
|     - ParentOrderId = UUID                                                                         |
|     - SagaState = 'PENDING'                                                                        |
|     - ExpectedChildCount = 3                                                                       |
|     - LeaseExpiresAt = NOW() + 60s                                                                 |
|         |                                                                                          |
|         +---> Loop: For each Supplier in cart:                                                     |
|         |        Create Child Order (Status: PENDING, ParentOrderId: UUID)                         |
|         |        Append ChildOrderId to CreatedChildOrderIds                                       |
|         |                                                                                          |
|         +--[All Children Created Successfully]----------------------------------+                  |
|         |  - Update ParentOrders: SagaState = 'COMMITTED', Status = 'CONFIRMED' |                  |
|         |  - Emit PARENT_ORDER_CREATED event via Outbox                         |                  |
|         |                                                                       |                  |
|         +--[Transient Error / Partial Failure]                                  |                  |
|            - Wait for Lease Expiry...                                           |                  |
|                                                                                 v                  |
|  [Background Saga Recovery Worker] (order.StartSagaRecoveryWorker - runs every 15s)                |
|     - Queries Idx_ParentOrders_SagaRecovery (SagaState='PENDING', LeaseExpiresAt < NOW())          |
|     - If ChildCount == ExpectedChildCount: Mark COMMITTED                                          |
|     - If ChildCount < ExpectedChildCount: Transition to COMPENSATING:                              |
|          * Cancel all created child orders                                                         |
|          * Release inventory reservations                                                          |
|          * Mark SagaState = 'FAILED'                                                               |
+----------------------------------------------------------------------------------------------------+
```

- **Saga Recovery Worker**: Running every 15 seconds (`runtime_workers.go:114`), the recovery worker inspects the secondary index `Idx_ParentOrders_SagaRecovery` (`spanner.ddl:238`). If a pod crashed midway through creating child orders, the recovery worker cleans up orphaned children and marks the saga `FAILED`.

#### Why it is there
Distributed transactions across independent supplier organizations cannot be held open in a single long-lived database lock. The saga pattern with explicit lease timeouts guarantees eventual consistency and automated compensation.

## 3. Financial Ledger, Settlement & Soliq EHF Fiscalization

### 3.1. Integer Tiyin Minor Currency & Immutable Double-Entry Ledger

#### What it is
PegasusX manages all monetary values in **integer minor units** (e.g. Uzbek Tiyin: 1 UZS = 100 Tiyin). Floating-point representations are strictly prohibited across all databases, API payloads, and client applications.

#### How it works
- **Double-Entry Ledger Table** (`file:///Users/shakhzod/Desktop/V.O.I.D/pegasusX/apps/backend-go/schema/spanner.ddl:660-684`):
  Every financial movement creates an immutable append-only record in `PaymentLedgerEntries`:
  ```sql
  CREATE TABLE PaymentLedgerEntries (
    EntryId         STRING(36)   NOT NULL,
    SessionId       STRING(36)   NOT NULL,
    OrderId         STRING(36)   NOT NULL,
    SupplierId      STRING(36)   NOT NULL,
    Gateway         STRING(32)   NOT NULL,
    EntryType       STRING(32)   NOT NULL, -- CAPTURE, REFUND, CHARGEBACK, SETTLEMENT
    AmountMinor     INT64        NOT NULL,
    Currency        STRING(3)    NOT NULL,
    ReferenceId     STRING(128)  NOT NULL,
    CreatedAt       TIMESTAMP    NOT NULL OPTIONS (allow_commit_timestamp=true),
  ) PRIMARY KEY (EntryId);
  ```
- **Strict Unique Index**: `Idx_PaymentLedgerEntries_GatewayTypeRef ON PaymentLedgerEntries(Gateway, EntryType, ReferenceId)` (`spanner.ddl:682-683`) ensures that duplicate payment webhooks or retries can never record duplicate ledger debits or credits.

#### Why it is there
Floating-point rounding errors accumulate across thousands of daily transactions, causing balancing discrepancies between bank statements and system records. Integer minor arithmetic guarantees mathematically exact accounting.

### 3.2. Cash Reconciliation & Driver Shortfall Escalation

#### What it is
A high percentage of wholesale FMCG deliveries in Central Asia are settled via physical cash upon delivery. PegasusX implements an end-to-end cash custody and reconciliation system (`file:///Users/shakhzod/Desktop/V.O.I.D/pegasusX/apps/backend-go/cashreconroutes/routes.go`).

#### How it works
1. **Driver Cash Collection**: At each stop, the driver collects cash from the retailer (`POST /v1/order/collect-cash`).
2. **Shortfall / Overage Tracking**: If the retailer pays less than the invoice total, the driver records the shortfall. The backend emits `CASH_SHORTFALL` (`events.go:218`) and automatically creates an open item in Accounts Receivable for the difference.
3. **Cash Hand-In & Verification**: At the end of the shift, the driver returns to the warehouse cash office, handing in physical banknotes. The cashier counts the money and enters the counted total (`POST /v1/cash-recon/shifts/{id}/submit-handin`).
4. **Nightly Escalation Worker**: The `CashReconEscalation` worker (`runtime_workers.go:122`) audits all closed driver shifts. Discrepancies exceeding allowable thresholds are escalated to finance management, freezing the driver's manifest dispatch eligibility.

### 3.3. Accounts Receivable (AR) Dynamic Dunning

#### What it is
When goods are delivered on credit (`DELIVERED_ON_CREDIT`), the system initiates Accounts Receivable tracking (`file:///Users/shakhzod/Desktop/V.O.I.D/pegasusX/apps/backend-go/ar/service.go:1-60`).

#### How it works
- **AR Invoice Creation**: Upon credit delivery, the backend writes an `ARInvoices` row:
  - Fields: `InvoiceID`, `SupplierID`, `RetailerID`, `OrderID`, `PrincipalMinor`, `BalanceMinor`, `TermsDays`, `GracePeriodDays`, `AgingBucket`, `DunningStep`, `LastDunnedAt`.
- **Dynamic Aging Buckets**:
  - `CURRENT`: Within agreed credit terms (e.g. 14 days).
  - `1_30`: 1 to 30 days overdue.
  - `31_60`: 31 to 60 days overdue.
  - `61_90`: 61 to 90 days overdue.
  - `90_PLUS`: Severe delinquency.
- **Hourly Dunning Daemon** (`runtime_workers.go:188`): The `ARDunningWorker` evaluates overdue invoices every hour. Based on the aging bucket, it sends progressive dunning notifications (SMS, push, email). If an invoice crosses into `31_60`, the retailer's credit ordering privileges are automatically locked (`RETAILER_CREDIT_LIMIT_BREACHED`).

### 3.4. Uzbekistan Soliq EHF Fiscalization (ADR-009)

#### What it is
Uzbekistan law mandates that all wholesale transactions be registered electronically with the State Tax Committee (**Soliq**) via an authorized Operator of Fiscal Data (OFD), generating an electronic invoice (Elektron Hisobvaraq-Faktura - EHF).

#### How it works
PegasusX implements ADR-009 fiscal hard-gating (`file:///Users/shakhzod/Desktop/V.O.I.D/pegasusX/apps/backend-go/soliq/client.go:1-60`):
1. **Fiscal Request Trigger**: Once payment is cleared or credit terms are accepted, the order transitions to `FISCALIZING` (`order/service.go:61`), and an outbox event `FISCAL_RECEIPT_REQUESTED` is published.
2. **OFD Memory Registration**: The Soliq client transmits order line items, national commodity classification codes (MXIK), packaging units, excise marks, and VAT percentages to the OFD gateway.
3. **Fiscal Receipt Record**: Upon successful receipt generation, the backend creates an immutable record in `OrderFiscalReceipts` (`spanner.ddl`) storing the official QR fiscal URL, fiscal sign (`FiscalSign`), and Soliq invoice ID.
4. **Order Completion**: Order status transitions to `COMPLETED`. If fiscal registration fails, the order transitions to `FISCAL_FAILED`, triggering an administrative alerting queue.
5. **Buyer Acceptance Poller**: The background worker `BuyerAcceptancePoller` (`runtime_workers.go:193`) queries the tax portal every hour to verify that the retail store owner has electronically signed the Soliq EHF document using their digital signature (E-Imzo).

### 5.2. Last-Mile Logistics Exceptions

PegasusX is built to handle the inevitable chaos of real-world urban delivery:

1. **Shop-Closed Exception Handling** (`order/service.go:57`, `events.go:260-264`):
   - When a driver arrives at a retailer and finds the store locked, they mark the stop `SHOP_CLOSED_PENDING`.
   - The system starts a **grace period countdown** (e.g., 10 minutes), sending urgent automated push notifications and phone calls to the store owner.
   - If the retailer opens within the grace window, the driver proceeds with normal delivery.
   - If the timer expires (`SHOP_CLOSED_TIMEOUT`), the system logs `SHOP_CLOSED_ESCALATED`, releasing the driver to the next stop and re-routing the undelivered pallets back to the warehouse reverse-logistics bay (`apps/backend-go/returnsroutes/`).
2. **Proximity Unlocking**:
   - To prevent fraudulent offloads or premature handoffs, the driver application cannot initiate QR scanning or payment collection until the device GPS coordinates enter within a **100-meter radius** of the retailer's registered storefront (`ProximityUnlockedAt`).
3. **Partial Delivery Offload**:
   - If half the goods are damaged or rejected by the retailer, the driver marks `PARTIAL_OFFLOAD` (`events.go:271`). The invoice is dynamically recalculated in integer Tiyin, the accepted goods are delivered, and a return authorization is created for the rejected inventory.
4. **Credit Leave-Behind**:
   - If the retailer has insufficient cash on hand but possesses an active credit line, the driver marks `CREDIT_LEAVE` (`events.go:272`). Custody is transferred, and an Accounts Receivable invoice is generated (`ar.Invoice`).
5. **Warehouse Split Shipments** (`events.go:247-254`):
   - When a single retailer places an order exceeding the volume capacity of any single delivery truck (`ORDER_CAPACITY_OVERFLOW`), the warehouse supervisor approves splitting the order across multiple vehicles (`SPLIT_SHIPMENT_CREATED`).
   - The system coordinates payment across the split runs: payment is locked so only the first arriving driver collects cash, while subsequent drivers deliver remaining pallets under the cleared transaction authorization.
